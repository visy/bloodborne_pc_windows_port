# Saves, backups and the game file check

Back to the [README](../README.md).

- **Save safety**: save files are written to a temporary copy and moved into place when the game closes them, so a crash in the middle of saving leaves the previous save intact (`BB_SAVE_TRACE=1` logs every save file operation). At start the game checks its save files (sizes, an emptied game-data file, characters missing compared with the newest backup) and logs `Saves: check OK` or a warning.
- **Party saves and backups**: a party session always plays from `user\savedata_party` (launcher or in-game start; the title's own *Continue* / *New Game* stay single-player), so `user\savedata` (single-player) is never written by it; the first time, the launcher offers to copy the single-player save (it only reads it; also the *Copy single-player save to party save* button). In a party session the game copies the active save folder to `user\save_backups\<folder>\<date>-<time>-<reason>\` at start and every 10 minutes (`BB_SAVE_BACKUP=0|1`, `BB_SAVE_BACKUP_MINUTES`, `BB_SAVE_BACKUP_KEEP`, default 10 kept; unchanged saves are not copied again). A copy that fails the check is kept as `...-suspect` and never pushes good backups out, so a crash that damages the save cannot rotate the last good one away. **Restore**: close the game, rename the save folder (e.g. `user\savedata_party` to `savedata_party.broken`), create it again and copy the backup folder's contents (the numbered folder, not `BACKUP_INFO.txt`) into it; `user\save_backups\README.txt` has the same steps.
- **Undo last party session** (0.6.2): right before every party session the game copies both save folders to `user\save_backups\party_sessions\<time>-host|guest`; the launcher's *Party* tab puts them back byte for byte after showing what it replaces (the current saves are kept the same way, so the undo can be undone), and checks the party save after each session (every character loads, NG cycle, boss kills and lamps, level and play time) and offers the undo when something looks wrong. Details: [party/save_safety.md](party/save_safety.md).
- **Saves from other builds** (shadPS4, other Bloodborne PC ports, another region's game): the game reads `user\savedata\1\<title id>\SPRJ0005\` (`user\savedata_party\...` in a party session); `<title id>` is your game's (`CUSA00207` US, `CUSA03173` EU, `CUSA00900` JP, ...; the launcher log's `Runtime: save data` and `Saves:` lines show the folder). To bring a save over, close the game and copy the other build's `savedata` folder contents (the numbered user folder with the title folder in it) into `user\savedata`; for party play then use the launcher's *Copy single-player save to party save* (it replaces the party save as a whole and backs the old one up; copying files over an existing `savedata_party` by hand leaves the old party save's extra files behind). At the next start the game takes the save in by itself and says so in the log:
  - **shadPS4's layout** (`SPRJ0005\sce_sys\param.sfo` inside the folder, no `SPRJ0005.sce_sys` beside it) is read as it is; the description is copied to our `SPRJ0005.sce_sys\param.bin`, and our port writes `sce_sys\param.sfo` inside the folder too, so the same folder opens in shadPS4 again (`BB_SAVE_SFO=0`: not written).
  - **Another user id or title id** (e.g. `savedata\1000\...`, or an EU save with a US game): when the folder this game reads has no save, the newest Bloodborne save under another user id or region is copied there (the original stays); a save copied one folder too deep or too shallow is named in the log with where it belongs.
  - Saves from the other Bloodborne PC ports (Mrsuss60's, Supermedo's, deadinside28's) already use our layout and load as they are; the Bloodborne Save Editor's `*.bak` copies next to the files are ignored.
- **Game file check**: the launcher and `run.bat` check that the game folder holds the 1.09 executable (the base game 1.00 crashes at start) and say what is missing; `BB_SKIP_GAME_CHECK=1` skips the check. A dumped update is a separate folder: copy it over the base game, replacing files. Plain ELF `eboot.bin` dumps (without the SELF wrapper) are accepted too.
- **Save editor** (launcher, Party tab, *Save editor...*; `scripts/saveedit`): edits one character of a single-player or party save. Pages: *Character* (name, the six stats with the level calculated from them, Blood Echoes, Insight, NG cycle), *Items* (counts up to what the game lets you hold, remove, weapon level, **Add item...**: weapons at +0, armor and items from your own game's lists), *Gems* (a blood gem's effects, **Add blood gem...** in any shape, **Add rune...** from the game's Caryll and oath runes, **Copy selected**), *Progress* (boss kills, lamps, endings, any flag by id; reviving Ludwig also clears his second flag, a lamp is its three flags) and *Party* (repairs: the phantom mark, doubled key items). A save the game wrote as a guest in another world opens as it is (the editor works on a copy with the world-state section filled in and writes the game's own back; no export or import needed). Safety: it refuses while a game runs, shows what will change in words and asks first, copies the whole save folder to `user\save_backups\<savedata|savedata_party>\<time>-before-edit` (the last 20 are kept; *Backups...* restores one and first keeps the current saves), writes through a temp file, reads the result back and puts the backup back on any difference. Adding a weapon, armor piece or gem moves the data behind the item table by the record's size and leaves the header's offsets as they were (the game rewrites the header at its next save); the layout is in [docs/party/save_layout.md](party/save_layout.md). Item, gem, boss and lamp names come from your own game folder (nothing of the game's text ships). Checked: unit tests on synthetic saves and on the test saves; the game loaded an edited copy with a new item, weapons, armor and gems and its inventory screen listed the new item (the weapon, armor and gem tabs and a save made by the game afterwards were not checked).
